# Supported Recipe Pages

The NeoForge 1.21.1 editor supports two layers of JEI recipe pages: the vanilla
types, which have a dedicated adapter each, and the declared mod layer, one
declaration per mod recipe type.

The authoritative, per-page list is **[JEI_PAGE_COMPAT_TODO.md](JEI_PAGE_COMPAT_TODO.md)**.
It is generated by `scripts/jei-category-dump/gen_checklist.py` from a runtime
export of the development client and is the only place that enumerates every
registered page and its status (`done` / `declared` / `gap` / `todo`). Do not
duplicate its tables here. The procedure for turning one more page into an
editable one is **[JEI_PAGE_COMPAT_WORKFLOW.md](JEI_PAGE_COMPAT_WORKFLOW.md)**.

As of the last generated checklist (and the last `jei-verify` run): 188 pages are
registered in the development environment; 91 are wired for editing — the 13
vanilla pages below plus the mod pages that carry a declaration or that display a
vanilla recipe the editor rebuilds itself. 31 pages are marked `gap` (nothing on
them can be patched) and none is left `todo`. The client page tests
(`scripts/jei-client-tests.ps1`) assert that every wired page models at least one
recipe and that every page marked `gap` — plus a separate known-unsupported list —
produces no model at all.

## Vanilla pages

Ten adapter rows cover the thirteen vanilla pages (four cooking pages share one
adapter, and the two smithing serializers share one page):

| JEI page | Adapter | Persistence |
| --- | --- | --- |
| Crafting | `CraftingRecipeEditorAdapter` | Targeted recipe JSON |
| Smelting, blasting, smoking, campfire cooking | `CookingRecipeEditorAdapter` | Targeted recipe JSON |
| Stonecutting | `VanillaSpecialRecipeEditorAdapter` | Targeted recipe JSON |
| Smithing transform and trim (`minecraft:smithing`) | `VanillaSpecialRecipeEditorAdapter` | Targeted recipe JSON |
| Fueling | `FuelRecipeEditorAdapter` | SavedData and fuel override |
| Brewing | `JeiVanillaRecipeEditorAdapter` | SavedData and brewing event override |
| Anvil | `JeiVanillaRecipeEditorAdapter` | SavedData and anvil event override |
| Grindstone | `JeiVanillaRecipeEditorAdapter` | SavedData and grindstone event override |
| Composting | `JeiVanillaRecipeEditorAdapter` | SavedData and `neoforge:data_maps/item/compostables` |
| Ingredient information | `JeiVanillaRecipeEditorAdapter` | Client model and SavedData |

The last five JEI types are generated views rather than `RecipeManager` JSON
entries. Their patches use the JEI UID as the identity. Brewing, anvil, and
grindstone edits are applied by their NeoForge runtime events; composting edits
are written to NeoForge's compostables data map and applied by the separate
Reload action. Information pages have no gameplay operation to override, so
their edits remain client-side display data.

A vanilla adapter claims only the serializer id it implements
(`RecipeEditorAdapters.isImplementedVanillaSerializer`), never the recipe's Java
class: a mod serializer whose recipe merely extends `ShapedRecipe` would be
rebuilt in the vanilla JSON shape and rejected by that mod's own codec. Such a
type must be declared instead, or deleted rather than edited.

## Declared mod pages

A mod recipe type has no per-mod reader or writer. Instead it has one
**declaration** (`ModdedRecipeAdapter`) that names, for that type:

- the recipe JSON field of every INPUT slot and every OUTPUT slot, in JEI display
  order, with `%d` for a repeatable field that names every remaining slot;
- the ingredient kind of each field (`withFieldKind` / `withFluidFields` /
  `withChemicalFields`, item by default), so a fluid or a Mekanism chemical slot
  is patched with its own field names rather than being written into an item node;
- the item encoding style (`{"item",...}` or `{"id",...}`) and, where a mod writes
  its non-item values differently, the fluid/chemical JSON style — including
  `ModdedJsonStyle.AMOUNT` for a field whose value is the bare amount, which then
  also has to pin its ingredient id (`withFixedFieldIds`);
- the optional flags a page needs: an ordered segment list
  (`withConcatenatedOutputs`), a page scope (`withPageUid`) for one serializer
  that JEI shows as two differently-oriented pages, the read-only page uids
  that share a serializer but cannot be written back, and
  `withPreservedIngredientBase` for an item field whose JSON is a *nested*
  ingredient node (Mekanism's painting input is a `neoforge:difference` with a
  `base` and a `subtracted`), where an edit rewrites only the node's `base` so
  `type`, `count` and `subtracted` survive verbatim;
- or, instead of the two field lists, a **recipe-derived slot sequence**
  (`DerivedSlotSequence`, implemented for Create's basin pages by
  `CreateBasinSlotSequence`), for a page whose slot sequence the mod synthesises
  from the recipe at display time — `create:mixing` / `create:packing` merge the
  item ingredients with equal `Ingredient.getItems()` into one slot each and put
  every item slot before every fluid one, which no field pattern can name. The
  client only checks the sequence's own count bound and the kinds it declares;
  the server resolves the whole sequence against the recipe JSON plus the recipe
  the mod loaded, writes a merged slot's value to every JSON entry it merged, and
  refuses the whole patch when the recipe does not fit the derivation.

The declarations are grouped per mod family —
`CreateRecipeDeclarations`, `ImmersiveEngineeringRecipeDeclarations`,
`MekanismRecipeDeclarations`, `CobblemonRecipeDeclarations`,
`SilentGearRecipeDeclarations`, `MiscRecipeDeclarations` — and aggregated by
`ModdedRecipeAdapters`, so adding a page never edits a shared list. The client
models a declared page from JEI's own slot views (`ModdedRecipeModelSupport`);
the server patches a copy of the recipe's original JSON in place
(`RecipeEditsApplier.createModdedRecipeJson`), so every field the edit did not
name survives untouched. The slot-key ↔ field rules both sides share are pure
and live in `common` (`RecipeFieldMapping`, `EditorIngredient`, `SlotPatchFields`).

Which types are declared, and with which fields, is exactly the A1/A2/B tables of
[JEI_PAGE_COMPAT_TODO.md](JEI_PAGE_COMPAT_TODO.md). A type whose JSON nests
ingredients or carries values a declaration cannot express stays undeclared and
is listed there as `gap`.

## Pages that display another recipe type's recipes

One page displays recipes the manager already holds, under an id of its own.
Mekanism's electric smelter page (`mekanism:smelting`) is built by
`MekanismRecipeType` out of the vanilla `minecraft:smelting` recipes, each renamed
by `RecipeViewerUtils.synthetic(id, "mekanism_generated")`, which inserts
`/mekanism_generated/` in front of the path — so JEI draws a `RecipeHolder` whose
id resolves nowhere while the recipe the game runs keeps its own id, serializer
and datapack JSON.

`RecipeViewerAliases` holds such a page's id rule (page uid → the path prefix the
page inserts). Both the editor and the client page tests resolve a displayed
recipe through it, so the page is modelled and patched as the recipe the manager
holds: the patch carries that recipe's id and serializer (here
`minecraft:smelting`) and travels the ordinary vanilla path. This is deliberately
not a `ModdedRecipeAdapter`: there is no mod serializer to describe, and a patch
naming the page's own rewritten id would have no recipe to write.

## Pages whose recipes are synthesised outside the recipe manager

A page can also show recipes that are in no registry at all. Those cannot be
edited by anything this editor does, and the generated checklist records the
measured provenance per family in "运行时合成页面的真实来源". Measured on the
68-jar pack with a temporary server-side probe: of the 8576 recipes in the
`RecipeManager`, **not one** lacks a resolvable recipe JSON, and the synthesised
entries of Create's draining/spout pages, IE's arc recycling, Just Enough
Archaeology's brush/sniff pages and Mekanism's smelting alias are in no registry
— Create's runtime `DynamicPack` carries only its cutting and washing recipes. `RecipeEditsApplier`
therefore never sees such an id: the import gate refuses it before a file is
written, which is what `scripts/jei-declared-smoke.ps1` asserts per family.
